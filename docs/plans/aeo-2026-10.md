## 1. Goal and acceptance criteria

**Goal.** Raise Lanshore's citation rate in answer engines by (a) closing the nine
structured-data and on-page-structure gaps the HubSpot AEO tool flagged, and
(b) publishing the 30 owned pages that target the prompts where Lanshore is
currently absent from the answer set.

**Acceptance criteria — measurable and falsifiable:**

| # | Criterion | How it is checked |
|---|-----------|-------------------|
| AC1 | Every blog post and case study emits `BlogPosting`/`Article` JSON-LD carrying `author`, `dateModified`, and `image`; `datePublished` is present **when and only when** a real publish date is on file. Never guessed, never defaulted. | `node --test src/lib/schema.test.mjs`; grep built HTML for `datePublished` |
| AC2 | Every page that emits `datePublished` or `dateModified` renders that same date visibly in a `<time dateTime>` element. | `verify` skill browser pass, per route |
| AC3 | **Visibility mirror.** Every `FAQPage` question and answer, and every `HowTo` step name, that a page emits in JSON-LD also appears as visible text in that same page's rendered HTML. | `scripts/check-schema-mirror.mjs` over `.next/server/app/**/*.html`, wired into `postbuild` beside `check:headings` |
| AC3b | Additionally, `HowTo` step names appear as *headings* in the body, because a step that is not a section is not a step. | Same check, heading-aware for `HowTo` only |
| AC4 | The three `/agentic-spm/*/demo` routes have an unbroken outline: over `document.querySelectorAll('h1,h2,h3,h4,h5,h6')` no level step exceeds +1. | Heading-order assertion in the browser pass |
| AC5 | 8 `/solutions/<slug>` pages exist, each emitting `Service` + `FAQPage` + `BreadcrumbList`, each registered in NAV, `sitemap.xml`, `llms.txt`, and `contentDates.ts`. | `npm run build`; fetch `/sitemap.xml` and `/llms.txt` and count |
| AC6 | 10 `/resources/guides/<slug>` pages exist, each emitting `Article` (or `HowTo` where the content is a procedure) + `FAQPage` + `BreadcrumbList`, each in sitemap and `llms.txt`. | Same |
| AC7 | 11 new `/blog/<slug>` posts exist, each with Key Takeaways, FAQ, byline, dates, and `ItemList` JSON-LD on the 10 listicle/comparison pieces. | `npm run check:content`; build output grep |
| AC8 | All 29 new content files are registered in `content/SLUGS.lock.json` in the same commit as the file (ledger rule L3). | `npm run check:content` exits 0 |
| AC9 | Zero em dashes and zero emoji remain in **written copy** across `src/` and `content/`, with the documented exemptions in WP7 the only survivors, each listed in an allowlist the check reads. | `node scripts/check-house-style.mjs` exits 0 |
| AC10 | `npm run build` passes with zero new warnings; `npm run lint` exits 0; all five `prebuild` suites pass. | Command exit codes |
| AC11 | No fabricated fact ships. Every unverifiable claim appears as a literal `[PROOF POINT NEEDED: …]` marker, and the owner has seen the full list before merge. | `grep -rn "PROOF POINT NEEDED" content/ src/lib/` |
| AC12 | Every competitor claim on the 5 comparison pages is traceable to a dated public source recorded in the page's `sources[]` frontmatter. | Validator requires `sources[]` non-empty on `type: comparison`; owner review |

**Explicitly NOT an acceptance criterion:** any movement in the HubSpot AEO
opportunity scores. A third party measures those on their own cadence; this repo
cannot gate on them.

### User impact

Visible byline, publish and update dates, Key Takeaways and FAQ blocks appear on
19 existing detail pages. 29 new URLs go live. Punctuation changes on essentially
every page. No existing URL changes, nothing is removed.

### Data and migration risk

No database. The only migration-shaped change is a possible single image rename
(WP4), done as a rename plus reference update in one commit.

### Shared-lib risk

`src/lib/schema.ts` is the highest-leverage file in the repo. All changes there
are additive: new optional parameters and new exported builders. No existing
function signature changes in a breaking way.

### Rollback

Every work package is an independent commit. `git revert` of any one leaves the
site building. WP7 (house style) is deliberately **last** among the site-wide
passes so that reverting it does not drag content work with it.

### WP2 — HowTo, Key Takeaways, FAQ and the mirror rule (closes 1.2, 1.6)

1. **`howToSchema()`** in the schema layer, taking
   `{ name, description, totalTime?, steps: [{ name, text, anchor? }] }` and
   emitting `HowTo` with `HowToStep` items and `url` anchors back into the page.

2. **New frontmatter: `howTo`, `keyTakeaways`.** Validated in
   `content-rules.mjs`.

3. **The mirror rule, enforced against build output, not front matter.**
   This is the point of the work package, and the cold review changed how it
   has to be built. The original design put the rule in `content-rules.mjs`,
   which only ever sees `content/` files. But FAQs also live in
   `src/lib/spmPlatforms.ts` and will live in `src/lib/solutions.ts`, so a
   front-matter-only rule cannot see the majority of the site's FAQ schema.

   The rule therefore lives in a new `scripts/check-schema-mirror.mjs` that
   reads `.next/server/app/**/*.html`, parses every `application/ld+json`
   block, and asserts that each `FAQPage` question and answer and each `HowTo`
   step name also appears as visible text in that same file. It runs in
   `postbuild` beside `check:headings`, and it covers every page on the site
   regardless of where its data came from.

   Note the corrected requirement: Google's rule is that the marked-up content
   be **visible**, not that it be a heading. `FaqSection` renders `<dt>`/`<dd>`,
   which is valid, visible, and arguably the better markup for Q&A. So
   `FaqSection` is **not** rewritten and the "No redesign" non-goal holds.
   `HowTo` steps are the exception and are heading-checked, because a step that
   is not a section heading is not a step.
   *Verify:* the check must fail on a synthetic page whose FAQ schema contains a
   question absent from the body, the same way `check-headings.mjs` was proven
   against a mutated build artifact.

4. **`src/components/KeyTakeaways.tsx`** (new), rendered above the article body.

5. **Populate `howTo`** on the territory white space post from its existing
   "Step 1" through "Step 5" headings. No new prose: the procedure is already
   written and already uses step headings.

6. **Populate `keyTakeaways` and `faq`** on the two posts the brief names

*Verify:* `npm run build`; Rich Results Test on the territory post returns a valid

   allowlist. Wire it into `prebuild` **after** the pass lands, not before.
2. **Exemptions, each recorded in the allowlist with a reason:**
   - The demo-UI dingbats `✓ ✕ ⚠ ⚑ ✉` in `CustomAppDemo`, `DemoDashboard`,
     `OperationsDemo`. These are interactive UI chrome, not written content.
   - `GARTNER_2019.disclaimer` — a verbatim legal string. Not ours to edit.
   - `GARTNER_2019.claims.heritage` contains one em dash. It is Lanshore's own
     paraphrase rather than a Gartner quote, so it *can* change, but it is the
     site's most legally sensitive sentence. **Owner sign-off required (OQ3).**
   - **Em dashes inside code, not copy.** `serviceSchema()` hardcodes one in a
     JSON-LD `name` emitted on every pillar page; changing it changes structured
     data, not prose. Regex character classes are a second case: `headline()`
     had one and it has since been rewritten as `—` in `schema-nodes.mjs`,
     which is the pattern to follow rather than exempt.
   - **`src/lib/spmPlatforms.ts` holds 48 of them**, many inside
     `metaDescription` and `firstSentence`. These are the strings Google prints
     and answer engines lift. They are the highest-stakes edits in the whole
     plan and must be reviewed one at a time by the owner, not batch-edited.
3. **Define "written copy" before starting.** AC9 is unreviewable until this is
   settled. The working definition: strings a reader or a crawler sees, which
   means JSX text, `metaDescription`, `titleTag`, `firstSentence`, JSON-LD
   values, and `alt` text. It does **not** mean code comments, which are not
   published. The checker must therefore parse, not grep blindly.
4. **Convert in passes, smallest blast radius first:** `content/` (18 files),
   then `src/lib/` data files, then `src/components/`, then `src/app/`. Each pass
   is its own commit. An em dash becomes a period, semicolon, colon, comma or
   parenthesis depending on what the sentence is doing. This is editing, not
   find-and-replace, and a blind `sed` will produce run-on sentences.
5. **HTML entities.** `&mdash;` appears **zero** times in this repo; an earlier
   draft of this plan claimed otherwise and was wrong. `&rsquo;` appears 17
   times and `&amp;` is common. The checker should still handle the entity forms
   so a future one cannot slip in, but there is no existing `&mdash;` cleanup to do.

*Verify:* `node scripts/check-house-style.mjs` exits 0; `npm run build` compares
clean against expectation **after** build-hash normalization — raw HTML byte diffs
on this repo are all false positives without it.

## 5. Testing strategy

All five suites are real and wired into `prebuild` (see WP0):

- `npm run test:rules` → `scripts/lib/content-rules.test.mjs`
- `npm run test:loaders` → `src/lib/content/loadContent.test.mjs`
- `npm run test:auth` → eight studio suites
- `npm run test:redirects` → `scripts/lib/redirect-destinations.test.mjs`
- `npm run check:content`, `npm run check:admin`

New tests land in `content-rules.test.mjs` (pure, no on-disk fixtures, matching
that file's stated design) and a new `src/lib/schema.test.mjs` covering the
`.mjs` schema builders.

### Edge and negative cases — at least one per new behavior

| Behavior | Positive | Edge / negative |
|----------|----------|-----------------|
| `datePublished` validation | valid ISO date accepted | `2026-02-30` rejected; `datePublished` after `dateModified` rejected |
| `author` validation | known id accepted | unknown id rejected; non-string rejected |
| `blogPostingSchema` author | `Person` node when author set | Organization `@id` when author absent |
| `blogPostingSchema` dates | `datePublished` emitted when present | key **absent** — not null, not empty string — when not supplied |
| `image` fallback | record image used when present | site OG image when absent; never an empty string |
| `howToSchema` | steps emitted in order with anchors | empty `steps` array rejected at validation |
| HowTo mirror rule | step name matching a body heading passes | step name with no matching heading fails the build |
| FAQ mirror rule | question matching a body heading passes | question with no matching heading fails the build |
| `itemList` validation | items emitted in source order | fewer than 2 items rejected (a list of one is not a list) |
| `sources[]` on comparisons | non-empty array accepted | `type: comparison` with empty or missing `sources` rejected |
| `solutions.ts` related case studies | known slug resolves | unknown slug throws at module load |
| `guides` collection in ledger | registered slug loads | unregistered file fails L3; retired slug without `redirectTo` fails L2 |
| house-style checker | allowlisted dingbat passes | a new em dash in `src/` fails; the `&mdash;` entity also fails |
| `headline()` truncation (existing) | unchanged | regression test that the 110-char behavior still holds |

### Coverage

The test commands are real, but no coverage instrumentation is configured, so the
coverage ladder bottoms out at `NO COVERAGE TOOL`. **Recommendation: add
`node --experimental-test-coverage` to the new suites** and report changed-file
percentage against the ≥80% bar. Node 20.9+ is already required by `engines`, and
every new behavior above is a pure function, which is what that flag measures
well. If it proves impractical, a `NO COVERAGE TOOL` waiver goes to
`docs/waivers/`.

## 6. Failure modes

| Failure | Likelihood | Detection | Mitigation |
|---------|-----------|-----------|------------|
| Fabricated statistics enter ~50,000 words of new content | **HIGH without discipline** | `grep -rn "PROOF POINT NEEDED"` plus owner review of every piece | Every unverifiable number is a marker, never a number. Non-negotiable, and the single biggest risk in this plan |
| A comparison page overstates or understates a competitor | **HIGH** — 5 pages, 10+ named vendors | `sources[]` validator plus owner review before merge | Every competitor claim traces to a dated public source recorded in frontmatter. See OQ4 |
| The em dash pass produces run-on sentences or changes meaning | **HIGH** — 572 edits | Read-through per pass; `npm run build` | Edit, never `sed`. One commit per directory so a bad pass reverts alone |
| Em dash pass touches the Gartner legal strings | MED | Checker allowlist; `git diff src/lib/site.ts` reviewed by hand | `disclaimer` is hard-exempt. `claims.heritage` is owner-gated (OQ3) |
| Golden-diff noise swamps review during WP7 | **HIGH** | Diff size | Build-hash normalization before any byte comparison — raw HTML diffs on this repo are all false positives without it |
| Schema emits `datePublished: undefined` or `""`, which is worse than omitting | MED | Schema unit test asserting key **absence** | Build the object with conditional spread, never assignment |
| FAQ or HowTo schema ships without matching visible content (Google spam signal) | **HIGH if unguarded** | Mirror-rule validator fails the build | The mirror rule is a hard gate, not advice |
| A new validator rejects existing valid content and breaks the build for everyone | MED | Run each new rule against all 19 existing files before wiring it into `prebuild` | Validate-then-wire, never wire-then-validate |
| A new public field leaks editorial state into the RSC payload | LOW | `assertNoAdminFields` already throws | Classify every new field explicitly in WP1 step 4 |
| Ledger rule L3 violation: a content file added without a `SLUGS.lock.json` entry | **HIGH without discipline** — 29 new files | `npm run check:content` fails | The ledger edit travels in the same commit as the content file, every time |
| A new page ships invisible: in the repo but not in sitemap, `llms.txt` or NAV | **HIGH** — 7 registration points, 29 new pages | A count assertion: sitemap entries == routes built | Drive registration from the collection, so adding a file registers it |
| A new guide or solution mentions Gartner and renders NO trademark attribution | **HIGH** | `Footer.tsx` builds `GARTNER_PATHS` from a hardcoded list plus `SPM_PLATFORMS` plus `BLOG_POSTS.filter(p => p.mentionsGartner)`; `derivesMentionsGartner` is called only in `loadBlog()` | Extend `derivesMentionsGartner` to the guides loader and to `solutions.ts` before any new page is written. Across 50,000 SPM words the chance that none says "Gartner" is near zero |
| A new `/solutions` or `/resources/guides` route collides with an existing route | LOW | `npm run build` route table | Both are fresh namespaces; `/resources/glossary` is a sibling, not a parent |
| Owner never supplies real publish dates, leaving 1.1 half closed | MED | `grep datePublished content/` | Ship the capability. An absent key is honest, valid schema. Do not backfill |
| 29 pages of copy land in one unreviewable commit | MED | PR size | One commit per page, or per small group. WP8/9/10 are explicitly per-piece |

## 8. UI/UX design

This plan touches UI, so gate 8 applies.

**Design reference.** No new design language. New components use existing tokens
(`text-ink`, `text-muted`, `border-line`, `bg-paper`, `text-accent`, `text-gold`)
and copy the visual grammar of the existing `FaqSection` (`max-w-4xl`,

`/spm/[slug]` page composition verbatim. `/resources/guides/[slug]` reuses the
`/blog/[slug]` composition verbatim.

**State inventory.**

| Component | States |
|-----------|--------|
| `AuthorByline` | author + both dates; author + updated only; no author (Lanshore org fallback); author with no LinkedIn (renders the name as plain text, never an empty link) |
| `KeyTakeaways` | present (2 to 6 items); absent (renders zero DOM nodes, no empty container) |
| `ComparisonTable` | populated; narrow viewport (horizontal scroll inside the container, never on the page); a cell with no value (renders an explicit "Not published", never a blank) |
| `FaqSection` (existing, reused) | unchanged |
| `/solutions/[slug]`, `/resources/guides/[slug]` | populated; unknown slug → `notFound()` |

**Accessibility criteria.**

- The byline author link is keyboard reachable with a visible focus ring and
  carries `rel="author"`. External links get `rel="noopener"`.
- Dates use `<time dateTime="YYYY-MM-DD">` so assistive tech reads a real date.
- `KeyTakeaways` is a `<section>` with an `<h2>` and a real `<ul>`, not styled divs.
- `ComparisonTable` is a real `<table>` with `<caption>` and `<th scope="col">`,
  not a grid of divs — which is also what makes it extractable by an answer engine.
- The WP3 heading fixes are themselves an a11y improvement: a screen-reader
  outline with no skipped levels.
- Contrast: no new color pair is introduced, so no new contrast risk.

**Falsifiable design acceptance criteria.**

- DC1: At 375px, the byline wraps with no horizontal page scroll.
- DC2: Tabbing from the article `h1` reaches the author link before the body.
- DC3: `KeyTakeaways` renders zero DOM nodes when `keyTakeaways` is absent.
- DC4: Heading-level deltas across every touched route are never greater than +1.
- DC5: `/solutions/<slug>` is indistinguishable in layout grammar from
  `/spm/<slug>` at the same viewport.
- DC6: `ComparisonTable` at 375px scrolls inside its container; the page does not.

## 11. Waivers

**1.4 — `Review` / `AggregateRating` on `/spm/compare`: NOT IMPLEMENTED.**

The page contains no reviews and no ratings. Emitting `Review` or
`AggregateRating` would mean publishing structured data asserting ratings that do
not exist. That violates Google's structured data policy — markup must represent
content visible on the page — and, because the page compares commercial software,
raises an FTC endorsement-guidance problem. The brief itself conditions the item
on real ratings existing, so skipping it is compliance with the recommendation,
not a departure from it. `Product` nodes inside the existing `ItemList` deliver
the extractable structure the item was actually after.

Durable waiver: `docs/waivers/aeo-2026-10-review-schema.md`.

**Coverage.** If `node --experimental-test-coverage` proves impractical, a
`NO COVERAGE TOOL` waiver goes to `docs/waivers/`.
