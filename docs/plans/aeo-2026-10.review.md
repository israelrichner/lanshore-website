## Top three weakest assumptions

**1. That `FaqSection` renders FAQ questions as headings, so the mirror rule works on `/solutions` and `/resources/guides`.**
It does not. `src/components/FaqSection.tsx` renders each question as a `<dt>`
inside a `<dl>`; the only heading it emits is the section `<h2>`. AC3 says
"every page emitting `FAQPage` has every `question` present as a heading," and
WP8 step 2 / WP9 step 2 both say to reuse `FaqSection`. So on day one, every new
`/solutions/*` and `/resources/guides/*` page violates AC3. The fix is either
rewriting `FaqSection` to emit `<h3>`, which changes four live surfaces
(`src/app/page.tsx:44`, `src/app/services/automation/page.tsx:248`,
`src/app/spm/[slug]/page.tsx:181`, `src/components/PillarPage.tsx:228`) and
contradicts "No redesign" in Non-goals, or restating AC3.

Compounding it: the mirror-rule validator is specified to live in
`scripts/lib/content-rules.mjs`, which `scripts/check-content.mjs` runs over
`content/` files only. FAQs for `/solutions` would live in `src/lib/solutions.ts`
and FAQs for `/spm/*` live in `src/lib/spmPlatforms.ts`. Neither is reachable by
that validator. AC3's "every page" is unenforceable by the mechanism the plan names.

**2. That "all five suites are wired into `prebuild`."**
Section 5 states this and AC10 restates it. The actual script was
`check:content && test:auth && test:loaders && test:redirects && check:admin`.
**`test:rules` was not in it.** The entire new validator test suite (mirror rule,
`datePublished` ordering, `itemList` minimum, `sources[]`) would never have run on
build. Nor does `npm run lint`. There is no `.github/workflows` directory: the only
automation is the pre-commit hook, which the prior cold review documented as
bypassable via an env-var prefix.

**3. That guides "inherit draft filtering, ledger rules L1 to L4, and the studio admin for free."**
Adding a `guides` collection requires edits to at least eleven places. WP9 step 1
names four. The missing ones: `scripts/check-content.mjs` (`readCollection`,
`onDiskRaw`, `livePaths`), `src/lib/studio/ledger-ops.mjs:23-24` (`DIR`, `EXT`),
`src/lib/studio/apply-action.ts:40-43` (`DIRS`), `src/lib/studio/validate.ts:28-32`
(`Ledger` shape), the `src/app/studio/(gated)/[collection]/[slug]/page.tsx` route,
a new `GuideForm.tsx`, `src/lib/content/loadContent.ts:81` (`CollectionKey`), and
the studio suites `ledger-ops.test.mjs` / `validate.test.mjs` /
`commit-payload.test.mjs`, which hardcode three collections. Also
`content/SLUGS.lock.json` asserts `version: 1` in `checkLedger`: decide whether a
new collection key is a version bump. A new engineer executing WP9 as written
ships a broken admin and a red `test:auth`.

## Missing failure modes

- **Concurrent writes to `content/SLUGS.lock.json`.** 29 content files each carry a
  mandatory ledger edit (L3), landing across many commits. Meanwhile the studio
  admin writes to `process.env.GITHUB_BRANCH ?? "main"` through `apply-action.ts`,
  with blob-sha conflict detection *per file*. Every studio Publish and every plan
  commit mutates the same single JSON file. The plan has no answer for whether the
  studio is frozen for the duration, or how 29 ledger entries merge against a
  moving `main`. Most likely source of a lost or duplicated registration.
- **Ledger ordering is display ordering.** `loadBlog()` ends in
  `byLedgerOrder(records, "blog")`. Where a new slug is appended decides where the
  post appears on `/blog` and `/resources`. The plan's priority ordering is about
  authoring order, not array position, so published ordering will be accidental.
- **Revert ordering is unconstrained.** Reverting WP1 after WP10 has landed 11 posts
  carrying `author:` and `datePublished:` leaves content that `validateBlogPost`
  rejects, and `check:content` is in `prebuild`, so the build breaks for everyone.
- **The two new site-wide gates have no measured baseline.** "Validate-then-wire" is
  stated for content rules only.
- **`solutions.ts` importing `CASE_STUDIES` pulls `fs` into its module graph.**
  `caseStudies.ts` does disk reads at module scope. Nothing states the allowed
  import direction.
- **The Gartner trademark footnote has no path for the new collections.**
  `src/components/Footer.tsx` builds `GARTNER_PATHS` from a hardcoded list plus
  `SPM_PLATFORMS.filter(...)` plus `BLOG_POSTS.filter(p => p.mentionsGartner)`.
  `derivesMentionsGartner` is called in exactly one place: `loadBlog()`. New guides
  and new solutions that mention Gartner render **no trademark attribution**. Across
  50,000 words about SPM, including five comparison pages naming vendors and analyst
  firms, the probability that zero pages say "Gartner" is close to zero. The plan
  does not mention `Footer.tsx` anywhere.
- **No CI at all.** Every criterion in sections 5 and 7 is a thing a human remembers
  to type.

## Undocumented prior knowledge

- **The "five registration points" are at least seven.** Add `Footer.tsx`
  (`GARTNER_PATHS`) and `/resources`.
- **`contentDates.ts` does not work the way "register it in `contentDates.ts`" implies.**
  `sitemap.ts` deliberately derives index `lastmod` from the collection rather than
  from `UPDATED`, with a header comment explaining why. A new engineer will add a
  flat `UPDATED.solutions` and reintroduce exactly that failure.
- **WP2 never states the FAQ heading level.** `Markdown.tsx` maps only `h2` and `h3`;
  `####` renders as an unstyled `<h4>`. Combined with the no-skip rule, the level is
  constrained.
- **`type: comparison` does not exist.** AC12 and WP10 step 3 both hinge on it.
  `validateBlogPost` has no `type` field and no step adds one.
- **`check-admin-isolation.mjs` has `A1_EXPECTED_COUNT = 7`** with a comment telling
  you not to increment it without justification.
- **The `verify` skill** is cited six times with no note of what a full pass over
  ~86 routes costs.

## Verification gaps

- **AC3** unenforceable for `src/lib/`-sourced pages; see assumption 1.
- **AC2** is written as a site-wide invariant with no enumeration and no mechanical
  check. Make it static: scan `.next/server/app/**/*.html` for a JSON-LD date and
  assert a matching `<time dateTime>` in the same file, the pattern
  `check-headings.mjs` already established.
- **AC5/AC6/section 7 step 4 contradict how `llms.txt` is built.** It lists pillars,
  platforms, industries and *index* pages. It lists `/blog`; it lists no individual
  post and no case study. Listing 11 new `/blog/*` URLs requires redesigning
  llms.txt, which is unplanned. `llms-full.txt` states it is composed entirely from
  `lib/*` sources "so it can never drift"; guides live in `content/`.
- **AC9's "written copy" is undefined.** Does a JSON-LD `name`, a `metaDescription`,
  an `aria-label`, or a code comment count?
- **AC11 is a grep for a marker the author also writes.** It proves markers exist,
  not that unmarked claims are true.
- **AC4 has already diverged from its implementation.** The branch ships
  `check-headings.mjs` enforcing three rules, not one. `EXEMPT_ROUTES` is empty.
- **AC10 "zero new warnings"** with no captured baseline warning list.
- **"No horizontal scroll at 375px" across 29 new pages** has no automation.
