## D4 — The source plan never specifies how content ordering survives the move to files

- **counts:** no
- **type:** plan-specification gap, found at T3, resolved additively within already-declared files
- **found:** T3 (migration)
- **detail:** Order is load-bearing — the plan's own §10.2 (`:702-703`) requires `ItemList` "numberOfItems and **ordering**" and sitemap "URL set, **order**" to be byte-identical. But content read from a directory is alphabetical, and:
  - none of the three arrays is in alphabetical order;
  - all five blog posts share `dateModified: 2026-07-11`, so date sorting cannot reproduce the order either.

  No task in P1 said how to preserve it. Reading files off disk in the obvious way would have silently reordered `/blog`, `/case-studies`, `/resources`, the sitemap, and every `ItemList` JSON-LD block — and the golden diff would have caught it only after four more tasks were built on top.
- **disposition:** `content/SLUGS.lock.json` becomes the canonical order. It is already an ordered array per collection, rule L3 guarantees every file appears in it, and the P3 admin already maintains it in the same atomic commit — so this adds no new concept. The file is **generated by T3** (which still knows the true order) rather than by T10 as the plan scheduled; T10 still owns `check-content.mjs` and the npm wiring.
- **why not counting:** the cap measures whether the *survey* misread the codebase. The survey was correct; the plan omitted a mechanism. The fix moves an already-declared artifact earlier in the same plan and widens no scope. Surfaced to the owner rather than silently absorbed.
